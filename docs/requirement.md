# LCR 要件定義（ユーザー起動用）

## 目的
- 本プロジェクトの実装は AI エージェントチームが担当し、本ドキュメントは起動時の要求仕様を定義する。
- 既存実装済みとされる Phase 4（Self-Learning Loop）について、現状の再検証を必須タスクとして実行する。

## 必須要件（Architect/PM/Implementer 共通）
- 要件ごとに検証可能なテスト観点を定義し、`src/` だけでなく `tests/` を成果物に含めること。
- 監査時の合否基準として `pytest tests/` が全件 Pass する状態を必須とすること。
- `docs/reference_standards.md` の規約（データ完全性、GUI アーキテクチャ標準、Humble Object パターン等）を遵守すること。

## Phase 4 再検証タスク（最優先）
以下を「再実行して結果を確認すること」を明示的に要求する。

### Phase 4: Self-Learning Loop
- Knowledge Update:
  ビルド成功時、ユーザー承認済みの「インポート名 ↔ パッケージ名」ペアをローカルナレッジベース（`library.json` / `user_knowledge.json`）へ自動追記する。
- Real-time Feedback:
  Docker ビルド進捗ログを GUI コンソールへリアルタイム表示し、進行状況を可視化する。
- Dynamic Refresh:
  新規作成環境を即時に UI リストへ反映し、アプリ再起動なしで実行できること。

### 再検証シナリオ（再チェック必須）
1. 「過去の遺産」の救済テスト  
   既存環境（例: `3.10test5`）再構築時に ID が保持され、知識適用によりビルド成功すること。
2. 「新規作成」の即時反映テスト  
   新規環境作成後に UI へ即時反映され、そのまま実行できること。
3. 「失敗とキャンセル」の安全性テスト  
   異常系でもクラッシュせず、停止・ロールバックが適切に機能すること。

### 合格基準
- ID消失なし（`custom-env` への化けなし）
- ログ完走（UIフリーズなし）
- 知識発動（旧パッケージ名を含む定義でも成功）
- 即時実行（再起動不要）
- クラッシュなし

## 実行指示
- エージェントは、上記再検証の実施結果を根拠付きで報告し、未達項目があれば修正計画と修正を実施すること。
- 監査担当は、`pytest tests/` 結果と規約準拠の両面で合否を判定すること。
