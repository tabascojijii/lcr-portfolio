# LCR 実装計画（Architect）

## 0. 前提・適用優先順位
- 絶対基準: `docs/reference_standards.md`。
- 要求仕様: `docs/requirement.md` を満たす。
- 注意: 指定された `docs/core_philosophy.md` はリポジトリ内に存在しないため、本計画は上記2文書を根拠として策定する。
- 合否判定の最終ゲートは以下2軸。
  - `pytest tests/` 全件Pass
  - `docs/reference_standards.md` 逸脱ゼロ

## 1. 目標
- Phase 4（Self-Learning Loop）の再検証を最優先で完遂する。
- 未達があれば、原因を規約ベースで切り分け、最小変更で修正する。
- 監査可能な証跡（ログ、ハッシュ、再現条件）を残す。

## 2. 要件トレーサビリティ（Requirement → Test/Implementation）

### R1: Knowledge Update
- 要件: ビルド成功時、ユーザー承認済みの「インポート名 ↔ パッケージ名」を `library.json` / `user_knowledge.json` へ自動追記。
- 実装方針:
  - 知識更新ユースケースを独立化（UIから分離）。
  - 追記前後でJSON整合性検証、重複排除、原子的書き込み。
- テスト:
  - 正常: 承認済みペアのみ追記される。
  - 異常: 書き込み失敗時にロールバックし、既存データ不変。
  - 回帰: 同一入力の再実行で重複生成しない。

### R2: Real-time Feedback
- 要件: Dockerビルド進捗ログをGUIコンソールへリアルタイム表示。
- 実装方針:
  - ビルド実行とログ配信を非同期ストリーム化。
  - Viewは表示専任（Humble Object）、整形はPresenter/ViewModel。
- テスト:
  - 正常: 長時間ビルドでUIがフリーズしない。
  - 完走: 開始から終了まで欠落なく表示。
  - 異常: ビルド失敗時もクラッシュせず終了状態を通知。

### R3: Dynamic Refresh
- 要件: 新規環境作成後、再起動なしでUIリストへ即時反映、実行可能。
- 実装方針:
  - 作成完了イベントを発火し、一覧データソースを再読込。
  - UI更新はスロット経由で一貫処理。
- テスト:
  - 正常: 新規環境が即時表示され、そのまま実行成功。
  - 回帰: 既存環境IDが保持され、`custom-env` へ化けない。

## 3. 再検証シナリオ実行計画（最優先）

### S1: 「過去の遺産」救済テスト
- 入力: 既存環境（例: `3.10test5`）を再構築。
- 検証:
  - ID保持（不変）
  - 知識適用によりビルド成功
  - 監査ログに結果記録

### S2: 「新規作成」即時反映テスト
- 入力: 新規環境を作成し直後に一覧確認。
- 検証:
  - 再起動不要で表示
  - 直後に実行できる

### S3: 「失敗とキャンセル」安全性テスト
- 入力: 意図的失敗条件およびキャンセル操作。
- 検証:
  - クラッシュなし
  - 停止・ロールバック成立
  - 中断時のデータ整合性維持

## 4. 参照標準に基づく実装制約

### 4.1 Docker再現性
- `FROM` はタグ禁止、digest固定必須。
- EOL OSはアーカイブリポジトリへリダイレクト。
- 依存解決は `constraints.txt` で探索範囲固定。
- C++ライブラリ（例: OpenCV）はマルチステージビルド。

### 4.2 データ完全性（ALCOA++）
- 実行ログに以下を必須記録:
  - コンテナイメージdigest
  - 実行時Gitコミットハッシュ
- 入出力・パラメータ・ログにSHA-256を付与。
- パスはプロジェクトルート相対で統一。

### 4.3 GUI/アーキテクチャ
- Humble Objectを強制（Viewはロジック最小化）。
- UseCase/EntityはQt非依存。
- 主要連携は `abc.ABC` または `typing.Protocol` 経由。
- 命名規約:
  - Signal: 過去分詞形（例: `buildFinished`）
  - Slot: 動詞（例: `update_console`）

## 5. 実装ステップ
1. 現状棚卸し
- Phase 4関連モジュール、Dockerfile、知識DB更新経路、GUI更新経路、テスト資産を特定。

2. テスト先行で再検証を固定
- 要件シナリオS1-S3を `tests/` に明文化（E2E + ユニット/統合）。
- 期待結果を合格基準に直接マッピング。

3. 不足機能の実装/修正
- Knowledge Update、ログストリーミング、Dynamic Refresh、失敗/キャンセル時の安全処理を最小差分で補完。

4. 標準準拠化
- Docker再現性、データ完全性、GUI分離規約への逸脱を是正。

5. 検証・監査証跡作成
- `pytest tests/` 実行。
- 再検証結果、ハッシュ、ログ、未達有無を監査可能形式で記録。

## 6. 監査ガバナンス運用定義（reference_standards第1章準拠）

### 6.1 客観的アーキテクチャ評価メトリクス
- M1: SRP違反
  - 判定条件: 1クラス/1モジュールが「知識更新」「Docker実行」「UI更新」など異種責務を2種類以上持つ場合はNG。
  - 証跡: 責務一覧表（クラス/関数ごとの責務ラベル）と差分上の該当箇所。
- M2: 依存方向違反（クリーンアーキテクチャ）
  - 判定条件: UseCase/Entity層からQt（`PyQt*` / `PySide*`）をimportしたらNG。
  - 証跡: import一覧スキャン結果。
- M3: 複雑度上限
  - 判定条件: 追加/変更した関数のサイクロマティック複雑度が10超でNG。
  - 証跡: 複雑度計測結果（対象関数名と値）。
- M4: テスト網羅条件
  - 判定条件: 要件R1-R3およびシナリオS1-S3に対し、正常系/異常系を最低1件ずつ欠く場合はNG。
  - 証跡: 要件-テスト対応表と `pytest` 実行結果。
- M5: 監査証跡完全性
  - 判定条件: 実行ログに「image digest」「git commit hash」「SHA-256」「相対パス記録」のいずれか欠落でNG。
  - 証跡: 監査ログ実ファイル。

### 6.2 Builder/Validator分離手順
- Builder（実装担当）の提出物を固定:
  - Diff（変更ファイル一覧と要約）
  - 要件対応表（R1-R3, S1-S3に対する実装箇所/テスト箇所）
  - 検証ログ（`pytest tests/` 結果、監査証跡ログ）
- Validator（監査担当）の情報境界:
  - 参照可能: 要件、絶対基準、Builder提出物（Diff/対応表/ログ）
  - 参照禁止: Builderの思考過程メモ、未確定作業メモ
- レビュー手順:
  1. 提出物の完全性確認（不足があれば即REJECT）
  2. メトリクスM1-M5を順に機械的判定
  3. 違反の有無を条項番号付きで記録
  4. PASS/REJECTを確定

### 6.3 REJECT時の処方的テンプレート（必須）
- 監査差し戻しは次テンプレートの全項目を必須とする。
  - 失敗箇所: `file path` と対象関数/手順
  - 違反基準条項: `docs/reference_standards.md` の章・条項番号
  - 違反内容: 事実ベースで簡潔に記述
  - 修正指示: 実施手順を番号付きで具体化
  - 再提出条件: 追加すべきテスト/証跡を明記

## 7. 成果物
- 実装コード（`src/`）
- テストコード（`tests/`）
- 監査証跡（再検証ログ、ハッシュ、実行条件）
- 逸脱があった場合の修正履歴と根拠

- S1-S3すべて合格。

  - ログ完走（UIフリーズなし）
  - 知識発動
  - 即時実行（再起動不要）
  - クラッシュなし
- `pytest tests/` 全件Pass。
- `docs/reference_standards.md` 逸脱ゼロ。
