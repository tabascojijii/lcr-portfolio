# LCR 実装計画（Architect）

## 0. 前提と優先順位
- 絶対基準: `docs/reference_standards.md`（以下、基準書）を最上位とし、設計・実装・テスト・監査の全判断は基準書に従う。
- 要求入力: `docs/requirement.md` を満たす。
- 注意: 指定された `docs/core_philosophy.md` は現時点のリポジトリに存在しないため、本計画は `requirement.md` と `reference_standards.md` を根拠として策定する。

## 1. 実装対象（最優先）
`requirement.md` の最優先要求に従い、Phase 4（Self-Learning Loop）の再検証を中心に、未達時は修正までを実施する。

- Knowledge Update:
  ビルド成功時に、ユーザー承認済み「インポート名 ↔ パッケージ名」ペアを `library.json` / `user_knowledge.json` に自動追記する。
- Real-time Feedback:
  Docker ビルド進捗ログを GUI コンソールへリアルタイム表示する。
- Dynamic Refresh:
  新規作成環境を UI リストへ即時反映し、再起動なしで実行可能にする。

## 2. アーキテクチャ方針（基準書準拠）

### 2.1 GUI/ドメイン分離（Humble Object + Clean Architecture）
- View は表示とイベント受け取りに限定し、状態遷移・検証・整形・永続化判断を UseCase/Presenter に移譲する。
- Qt 依存は外側（UI）に閉じ込め、内側のユースケース層は Qt 非依存とする。
- View と Presenter/UseCase 間は `Protocol` または `abc.ABC` のインターフェースを介して接続する。
- シグナル/スロット命名規約を統一する。

### 2.2 再現可能な Docker ビルド
- `FROM` はタグではなく digest 固定を必須化する。
- EOL ディストリビューションは archive リポジトリへリダイレクトする。
- 依存解決は `constraints.txt` により探索範囲を制限する。
- OpenCV 等のビルドはマルチステージを強制し、実行イメージ最小化と再現性を担保する。

### 2.3 データ完全性・監査証跡（ALCOA++ 対応）
- 実行ログに以下を必須記録:
  - コンテナイメージ digest
  - 実行時コミットハッシュ（`git rev-parse HEAD` の値をログへ記録）
- ログ/設定/スクリプト内のパスはプロジェクトルート相対パスで統一する。
- 入出力データ・パラメータ・実行ログへ SHA-256 を付与し改ざん検知可能にする。

### 2.4 マルチエージェント監査性
- Builder/Validator 分離前提で、差分のみでも判定可能な粒度で変更する。
- REJECT 時に修正指示が可能な構造（違反箇所と根拠が追跡可能）を実装・テストで担保する。

## 3. 実行計画（WBS）

### Phase A: 現状把握とギャップ抽出
- 目的: Phase 4 要求と現実装の差分を、基準書観点で特定する。
- 作業:
  - Self-Learning Loop 関連コード（知識更新、ビルドログ配信、UI リフレッシュ）を特定。
  - 3つの再検証シナリオを手動/自動で再実行し、結果を記録。
  - 基準書違反の有無を分類（UI分離、Docker再現性、監査証跡、エラーハンドリング）。
- 成果物:
  - ギャップ一覧（要件ID、違反基準、影響、再現手順）。

### Phase B: 修正設計
- 目的: ギャップを最小変更で閉じる設計を確定する。
- 作業:
  - UI/Presenter/UseCase の責務境界を明文化。
  - Dockerfile/constraints/ビルドパイプラインの固定化設計。
  - 監査ログスキーマ（digest, commit hash, sha256, 相対パス）を定義。
  - 異常系（失敗/キャンセル/ロールバック）の状態遷移設計。
- 成果物:
  - 修正方針メモ
  - テスト仕様（正常系・異常系・回帰）

### Phase C: 実装
- 目的: Phase 4 要求を満たすコード反映。
- 作業:
  - Knowledge Update の自動追記フローを実装（承認済みのみ反映）。
  - ビルド進捗の非同期ストリーミングを実装し UI フリーズを防止。
  - 新規環境の即時リスト更新と実行導線を実装。
  - 異常系の停止・キャンセル・ロールバックを実装。
  - 監査証跡（digest, commit hash, sha256, 相対パス）を実装。
- 成果物:
  - `src/` の修正差分

### Phase D: テスト実装と検証
- 目的: `pytest tests/` 全件 Pass と再検証シナリオ合格。
- 作業:
  - シナリオ1: 既存環境再構築時 ID 保持 + 知識適用成功
  - シナリオ2: 新規作成環境の即時反映 + 即時実行
  - シナリオ3: 失敗/キャンセル時の非クラッシュ + 安全停止
  - 監査証跡の記録項目・ハッシュ整合性の検証
  - UI 応答性（ログ完走、フリーズなし）の検証
- 成果物:
  - `tests/` の追加/更新
  - テスト結果ログ

### Phase E: 監査準備
- 目的: Auditor が REJECT/ACCEPT 判定可能な証跡整備。
- 作業:
  - 要件→実装→テストのトレーサビリティ表を作成。
  - 基準書各条項の準拠エビデンスを整理。
  - 未達がある場合は処方的修正計画（原因、修正点、再試験条件）を提示。
- 成果物:
  - 監査提出パッケージ

## 4. テスト観点（必須）
- 機能:
  - 知識ベース自動更新が承認済みペアに限定されること。
  - ログがリアルタイム表示され、完走すること。
  - 新規環境が再起動なしで実行可能になること。
- 回帰:
  - 既存環境IDが消失せず `custom-env` へ化けないこと。
  - 旧パッケージ名定義でも知識発動でビルド成功すること。
- 異常系:
  - ビルド失敗、ユーザーキャンセル、途中中断でクラッシュしないこと。
  - ロールバック後に不整合な中間状態が残らないこと。
- 監査性:
  - digest / commit hash / SHA-256 / 相対パス がログで確認できること。

## 5. 完了条件（Definition of Done）
- `pytest tests/` が全件 Pass。
- `requirement.md` の再検証3シナリオおよび合格基準を満たす。
- 基準書（`reference_standards.md`）に対する重大違反が 0 件。
- 監査で再現可能な証跡（実行手順・ログ・ハッシュ）が揃っている。

## 6. リスクと対策
- リスク: EOL 依存の取得不安定化。
  - 対策: archive ミラー固定、constraints 強化、ビルドキャッシュ戦略を併用。
- リスク: UI 層へのロジック逆流。
  - 対策: インターフェース境界を先に固定し、View テストではなく UseCase/Presenter テストを主軸化。
- リスク: 監査ログの欠損。
  - 対策: ログ出力を共通ユーティリティ化し、必須項目未設定時は実行を失敗させるガードを設ける。
