# LCR Requirements

## Phase 5: Validation Guardrails

### 1. 目的
- 動作不能な環境での実行を未然に防止し、実行結果と監査証跡の信頼性を担保する。
- スクリプト要求と実行環境能力のミスマッチを UI 上で明確化し、是正導線を強制する。

### 2. スコープ
- Environment Capability Mapping（環境能力可視化）
- ミスマッチ検知と実行ガード
- 強制作成フロー（適合環境が存在しない場合）

### 3. 用語と判定単位
- 判定単位は「配布パッケージ名」ではなく「import 名」とする。
- 例: `opencv-python` ではなく `cv2` を能力判定対象とする。

### 4. 機能要件

#### R5-1 Environment Capability Mapping
- 各環境について「動作可能 import 名リスト」を UI 上に明示すること。
- 能力データは以下を統合して生成すること。
  - `user_knowledge.json` の既知マッピング（import 名 ↔ package 名）
  - 実行実績（過去に当該環境で成功した import 検証結果）
- 能力表示は「推定（knowledge ベース）」と「実証（実行実績ベース）」を識別して表示すること。

#### R5-2 ミスマッチ検知と実行ガード
- スクリプト解析で抽出した required imports と選択環境 capability の差分を算出すること。
- 差分が1件でもある場合、`Run` ボタンを無効化すること（Hard Guard）。
- 警告 UI に最低限以下を表示すること。
  - 不足 import 一覧
  - 不足理由（未対応 / 未検証）
  - 推奨環境（存在する場合）
  - 新規環境作成への導線
- 既定動作として強制実行（ガード無視）は許可しない。

#### R5-3 強制作成フロー
- required imports を満たす既存環境が存在しない場合、ユーザーを新規環境作成ダイアログへ誘導すること。
- ダイアログ初期値には不足 import を補完する package 候補を自動投入すること。
- 生成候補は `user_knowledge.json` を第一候補とし、不足分は既定候補ルールで補うこと。
- 作成完了後は Phase 4 の Dynamic Refresh 要件に従い、再起動なしで選択・実行可能にすること。

### 5. 非機能要件
- 判定・UI更新は操作体感を阻害しないこと（フリーズ不可）。
- UI は Humble Object 原則を守り、判定ロジックは UseCase/Domain 側に置くこと。
- 監査ログには「required imports」「environment capability」「mismatch 結果」「ガード発火状態」を記録すること。

### 6. 受け入れ基準
- AC-1: 選択環境ごとに capability リストが UI に表示される。
- AC-2: required imports と capability が一致しない場合、Run は無効化される。
- AC-3: ミスマッチ警告に不足 import と推奨アクションが表示される。
- AC-4: 適合環境なしの場合、新規環境作成フローへ誘導される。
- AC-5: 作成後の環境が即時反映され、そのまま実行可能。

### 7. テスト要件（必須）
- `pytest tests/` 全件 Pass を必須とする。
- 最低限、以下の自動テストを追加すること。
  - T5-1 ガード発火テスト: ミスマッチ時に Run が無効化される。
  - T5-2 適合環境テスト: 要件一致時に Run が有効で実行できる。
  - T5-3 強制作成導線テスト: 適合環境なしで作成ダイアログへ遷移する。
  - T5-4 反映テスト: 作成完了後に即時実行可能となる。

### 8. 除外事項
- 本フェーズではクラウド同期や外部レジストリ照会は必須要件に含めない。
- 本フェーズでは強制実行の例外権限（管理者オーバーライド）は実装しない。

## Phase 6: Lifecycle Management

### 1. 目的
- 長期運用で増加する環境定義・Dockerリソースを安全に整理し、ストレージ圧迫を防止する。
- 削除・編集操作を監査可能にし、保守性と運用品質を維持する。

### 2. 採用方針（確定）
- P6-1 削除対象の範囲: **B**
  - 定義JSON + Docker image を削除対象とする。
- P6-2 一括削除の安全レベル: **B**
  - 2段階確認（対象件数/推定解放容量の確認 + 最終確認）を必須とする。
- P6-3 未使用判定基準: **C**
  - 最終利用日時 + 利用回数 + Pin/Favorite除外で判定する。
- P6-4 Dockerクリーンアップ範囲: **B**
  - dangling + 未使用 image を対象とする（build cache は対象外）。
- P6-5 リネーム方式: **C**
  - 表示名と説明のみ編集可能、内部IDは不変とする。
- P6-6 編集可能メタデータ: **C**
  - 表示名 + 説明 + タグ/分類 + 保護フラグを編集可能とする。
- P6-7 UI構成: **B**
  - 専用 Environment Manager ダイアログを実装する。
- P6-8 監査ログ粒度: **C**
  - 成功/失敗 + 対象一覧 + 解放容量 + 実行理由を記録する。
- P6-9 失敗時ポリシー: **B**
  - 部分失敗時は継続実行し、失敗分のみ報告する。
- P6-10 強制削除権限: **B**
  - 既定で不可、明示トグル操作時のみ許可する。

### 3. 機能要件

#### R6-1 Environment Manager UI
- 専用ダイアログを提供し、環境一覧・検索/フィルタ・複数選択・削除プレビューを提供すること。
- 削除プレビューには対象件数、対象名一覧、推定解放容量を表示すること。

#### R6-2 一括削除
- 削除対象は「定義JSON + 対応Docker image」とすること。
- 2段階確認を通過しない限り削除を実行してはならない。
- 処理は対象ごとの独立実行とし、1件失敗しても残り対象は継続処理すること。

#### R6-3 未使用環境の抽出
- 未使用判定は、最終利用日時・利用回数・保護フラグ（Pin/Favorite）を入力として算出すること。
- 保護フラグ付き環境は未使用候補から除外すること。

#### R6-4 Dockerリソースクリーンアップ
- dangling image と未使用 image をクリーンアップ対象に含めること。
- build cache / volume は本フェーズの対象外とすること。

#### R6-5 リネーム・メタデータ編集
- 内部IDは変更不可とし、表示名と説明を編集可能にすること。
- 追加でタグ/分類・保護フラグを編集可能にすること。
- 編集時は入力バリデーション（空値・長さ・禁止文字等）を適用すること。

#### R6-6 監査ログ
- 削除/編集/クリーンアップ操作ごとに監査ログを生成すること。
- 最低限、操作種別、実行時刻、対象一覧、成否、解放容量、実行理由を記録すること。

### 4. UX要件
- 一括削除は常に「理解可能な影響範囲」を事前表示すること（件数・容量・対象名）。
- 部分失敗時は、成功件数・失敗件数・失敗理由を分離して提示すること。
- 強制削除は既定で無効にし、ユーザーの明示トグル操作時のみ有効化すること。

### 5. 受け入れ基準
- AC6-1: 専用 Environment Manager ダイアログから複数環境を選択して削除できる。
- AC6-2: 削除前に2段階確認が必ず表示される。
- AC6-3: 未使用候補抽出で Pin/Favorite 環境が除外される。
- AC6-4: dangling + 未使用 image のクリーンアップが実行できる。
- AC6-5: 表示名/説明/タグ/分類/保護フラグの編集が可能で、内部IDは不変。
- AC6-6: 部分失敗時に処理継続し、結果サマリ（成功/失敗）が表示される。
- AC6-7: 監査ログに必要項目（種別、時刻、対象、成否、容量、理由）が記録される。

### 6. テスト要件（必須）
- `pytest tests/` 全件 Pass を必須とする。
- 最低限、以下の自動テストを追加すること。
  - T6-1: 2段階確認ガードテスト（確認未完了で削除されない）。
  - T6-2: 未使用判定テスト（最終利用日時 + 利用回数 + 保護フラグ）。
  - T6-3: 一括削除部分失敗テスト（失敗時も残り対象を継続）。
  - T6-4: リネーム/メタデータ編集テスト（内部ID不変）。
  - T6-5: クリーンアップ範囲テスト（dangling/unused のみ対象）。
  - T6-6: 監査ログ完全性テスト（必要項目の欠落なし）。

## Phase 6.1: Architecture Decoupling Assessment & Refactoring Proposal

### 1. 目的
- UIと業務ロジックの結合度を可視化し、保守性低下の根本要因を特定する。
- 依存方向違反・責務混在・Port未使用箇所を特定し、段階的な改善計画を策定する。

### 2. 成果物（必須）
- `artifacts/architecture_decoupling_assessment.md`
  - 現状のアーキテクチャ評価結果（違反一覧、影響、優先度）を記載すること。
- `artifacts/refactoring_proposal.md`
  - 改善方針、段階的移行計画、テスト戦略、リスク対策を記載すること。

### 3. 検証観点（必須）
- 依存方向違反（`UI -> UseCase -> Domain -> Infrastructure` に反する依存）
- UI責務混在（UI層での業務判断・永続化・外部I/O直接実行）
- 循環依存（モジュール間/層間）
- Port未使用または境界バイパス呼び出し
- テスト容易性低下要因（巨大クラス、直接依存、置換困難箇所）
- 依存関係の実測結果（importグラフ）に基づく違反件数と循環件数
- 変更影響テスト（UI変更時のDomain影響最小化 / Domain変更時のUI影響最小化）

### 4. 受け入れ基準
- AC6.1-1: 主要違反を `file path + 関数/クラス + 違反種別 + 根拠` で列挙している。
- AC6.1-2: 各違反に対して改善方針（移管先レイヤ、インターフェース設計）が定義されている。
- AC6.1-3: 改善計画は P0/P1/P2 の優先度と実施順序を持つ。
- AC6.1-4: 改善後の検証方法（追加/更新テスト、判定指標）が定義されている。
- AC6.1-5: importグラフ抽出結果として、`UI->Domain直参照` / `逆方向依存` / `循環依存` の一覧と件数が提示されている。
- AC6.1-6: 変更影響テストの実施手順（変更シナリオ、期待影響範囲、合否条件）が明記されている。
- AC6.1-7: 合否指標が数値で固定されている（例: 禁止依存0件、循環依存0件、UI層業務ロジック0件、境界テスト100% Pass）。

### 5. 実装・監査方針
- 改善案は「大規模一括置換」ではなく、段階的・後方互換を前提とすること。
- UI変更の影響を最小化するため、UseCase/Port経由の置換を優先すること。
- `pytest tests/` を必須ゲートとし、境界違反を検出するテスト追加を含めること。
- 疎結合性検証の成果物には、以下を必須で含めること。
  - importグラフの抽出手順と結果サマリ
  - 変更影響テスト結果（UI変更時/Domain変更時）
  - 数値合否指標の実測値と判定

## Phase 6.2: Pydantic Type Safety Introduction

### 1. 目的
- 境界DTOの型安全性を強化し、不正データを境界で即時検出（fail-fast）する。
- 段階導入により、前段階の実装失敗による大規模手戻りを回避する。

### 2. 採用方針（確定）
- P6.2-1 導入範囲: **A**
  - 境界DTOのみを対象とする（全面導入は本フェーズ対象外）。
- P6.2-2 バージョン方針: **A**
  - Pydantic v2 を固定採用する。
- P6.2-3 導入順序: **D**
  - A→B→C の順で段階導入する。
  - A: 監査メタデータDTO
  - B: Runtime判定DTO
  - C: 環境作成/更新DTO
- P6.2-4 バリデーション厳格度: **B**
  - strict 検証を採用し、型不一致は失敗とする。
- P6.2-5 失敗時挙動: **A**
  - fail-fast を採用し、型検証失敗時は処理継続しない。
- P6.2-6 互換方針: **A**
  - 新旧dictとの互換はアダプタ層で吸収し、段階移行する。
- P6.2-7 テスト要件: **C**
  - 正常系・異常系・シリアライズ互換の3系統を必須化する。
- P6.2-8 受け入れ基準厳格度: **B**
  - `pytest tests/` Pass + 型違反0件 + fail-fast動作確認を必須とする。

### 3. 機能要件

#### R6.2-1 DTOモデル化（段階導入）
- 境界DTOを Pydantic v2 モデルとして定義すること。
- 導入順は以下を必須とする。
  1. 監査メタデータDTO
  2. Runtime判定DTO
  3. 環境作成/更新DTO

#### R6.2-2 strict検証
- 対象DTOは strict 検証を有効化すること。
- 想定外キーや型不一致を黙殺しないこと（検証失敗として扱う）。

#### R6.2-3 fail-fast
- DTO検証失敗時は、当該処理を即時中断し、エラーを上位へ明示的に返すこと。
- 「警告のみで継続」は本フェーズで禁止する。

#### R6.2-4 互換アダプタ
- 既存dict入力との互換はアダプタ層で吸収すること。
- 既存呼び出し側を一括破壊せず、段階置換を可能にすること。

### 4. 受け入れ基準
- AC6.2-1: Phase 6.2 対象DTO（A/B/C順）が Pydantic v2 モデルで定義されている。
- AC6.2-2: strict 検証が有効で、型不一致入力が検証エラーになる。
- AC6.2-3: 検証失敗時に fail-fast で処理停止する。
- AC6.2-4: 互換アダプタにより既存dict経路が段階移行可能である。
- AC6.2-5: 型違反件数が 0 件である（既知未解決なし）。

### 5. テスト要件（必須）
- `pytest tests/` 全件 Pass を必須とする。
- 最低限、以下の自動テストを追加すること。
  - T6.2-1 正常系: 妥当DTO入力が受理される。
  - T6.2-2 異常系: 型不一致/必須欠落/想定外キーが検証エラーになる。
  - T6.2-3 fail-fast: 検証失敗時に後続処理へ進まない。
  - T6.2-4 互換: 既存dict入力がアダプタ経由でDTOへ変換できる。
  - T6.2-5 シリアライズ互換: JSON入出力で互換性を維持する。

## Phase 6.3: Static Type Gate (mypy/pyright)

### 1. 目的
- 実行時検証（Phase 6.2）に加え、静的型検証をCIゲート化して型不整合を事前に検出する。
- レイヤ境界の型契約（Port/DTO）を明示し、疎結合設計の破綻を早期に防止する。

### 2. 採用方針（確定）
- P6.3-1 検証対象
  - `src/` を対象に静的型検証を実行する（テストコードは段階導入）。
- P6.3-2 ツール方針
  - `mypy` を主ゲートとし、`pyright` は補助検証として導入可能にする。
- P6.3-3 段階導入
  - A: `core/use_cases/ports` を厳格化
  - B: `ui` 層を厳格化
  - C: 全体を厳格化
- P6.3-4 失敗時挙動
  - 型検証エラーは fail-fast（CI失敗）とする。

### 3. 機能要件

#### R6.3-1 型検証設定
- `mypy` 設定ファイルを追加し、対象パス・厳格オプション・除外範囲を定義すること。
- `pyright` を使う場合は設定ファイルを追加し、`mypy` と整合する対象範囲を定義すること。

#### R6.3-2 レイヤ境界の型契約固定
- Portインターフェース（`abc.ABC` / `typing.Protocol`）の引数・戻り値型を必須化すること。
- UseCaseの公開メソッドは戻り値型を明示し、`Any` の無制限利用を禁止すること。
- DTO境界（Phase 6.2導入モデル）を通るデータは型注釈を省略しないこと。

#### R6.3-3 Any/ignore管理
- `# type: ignore` は理由コメント付きでのみ許可し、無理由のignoreを禁止すること。
- `Any` の新規追加はレビュー対象としてカウントし、段階的に削減すること。

### 4. 受け入れ基準
- AC6.3-1: `mypy` が CI で実行され、エラー0件である。
- AC6.3-2: Port/UseCase公開メソッドで型注釈欠落がない。
- AC6.3-3: `type: ignore` は理由付きのみで、無理由ignoreが0件である。
- AC6.3-4: Phase 6.2 DTO境界を通る主要フローで `Any` 依存が段階目標以下である。

### 5. テスト・ゲート要件（必須）
- `pytest tests/` 全件 Pass を維持する。
- 型ゲートとして以下を必須化する。
  - T6.3-1: `mypy` 実行でエラー0件
  - T6.3-2: Port/UseCaseの型注釈チェック
  - T6.3-3: `type: ignore` 理由コメント検査
  - T6.3-4: `Any` 件数の差分監視（増加時Fail）
