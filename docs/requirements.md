# LCR Requirements

## Phase 5: Validation Guardrails

### 1. 目的
- 動作不能な環境での実行を未然に防止し、実行結果と監査証跡の信頼性を担保する。
- スクリプト要求と実行環境能力のミスマッチを UI 上で明確化し、是正導線を強制する。

### 2. スコープ
- Environment Capability Mapping（環境能力可視化）
- ミスマッチ検知と実行ガード
- 強制作成フロー（適合環境が存在しない場合）

### 3. 用語と判定単位
- 判定単位は「配布パッケージ名」ではなく「import 名」とする。
- 例: `opencv-python` ではなく `cv2` を能力判定対象とする。

### 4. 機能要件

#### R5-1 Environment Capability Mapping
- 各環境について「動作可能 import 名リスト」を UI 上に明示すること。
- 能力データは以下を統合して生成すること。
  - `user_knowledge.json` の既知マッピング（import 名 ↔ package 名）
  - 実行実績（過去に当該環境で成功した import 検証結果）
- 能力表示は「推定（knowledge ベース）」と「実証（実行実績ベース）」を識別して表示すること。

#### R5-2 ミスマッチ検知と実行ガード
- スクリプト解析で抽出した required imports と選択環境 capability の差分を算出すること。
- 差分が1件でもある場合、`Run` ボタンを無効化すること（Hard Guard）。
- 警告 UI に最低限以下を表示すること。
  - 不足 import 一覧
  - 不足理由（未対応 / 未検証）
  - 推奨環境（存在する場合）
  - 新規環境作成への導線
- 既定動作として強制実行（ガード無視）は許可しない。

#### R5-3 強制作成フロー
- required imports を満たす既存環境が存在しない場合、ユーザーを新規環境作成ダイアログへ誘導すること。
- ダイアログ初期値には不足 import を補完する package 候補を自動投入すること。
- 生成候補は `user_knowledge.json` を第一候補とし、不足分は既定候補ルールで補うこと。
- 作成完了後は Phase 4 の Dynamic Refresh 要件に従い、再起動なしで選択・実行可能にすること。

### 5. 非機能要件
- 判定・UI更新は操作体感を阻害しないこと（フリーズ不可）。
- UI は Humble Object 原則を守り、判定ロジックは UseCase/Domain 側に置くこと。
- 監査ログには「required imports」「environment capability」「mismatch 結果」「ガード発火状態」を記録すること。

### 6. 受け入れ基準
- AC-1: 選択環境ごとに capability リストが UI に表示される。
- AC-2: required imports と capability が一致しない場合、Run は無効化される。
- AC-3: ミスマッチ警告に不足 import と推奨アクションが表示される。
- AC-4: 適合環境なしの場合、新規環境作成フローへ誘導される。
- AC-5: 作成後の環境が即時反映され、そのまま実行可能。

### 7. テスト要件（必須）
- `pytest tests/` 全件 Pass を必須とする。
- 最低限、以下の自動テストを追加すること。
  - T5-1 ガード発火テスト: ミスマッチ時に Run が無効化される。
  - T5-2 適合環境テスト: 要件一致時に Run が有効で実行できる。
  - T5-3 強制作成導線テスト: 適合環境なしで作成ダイアログへ遷移する。
  - T5-4 反映テスト: 作成完了後に即時実行可能となる。

### 8. 除外事項
- 本フェーズではクラウド同期や外部レジストリ照会は必須要件に含めない。
- 本フェーズでは強制実行の例外権限（管理者オーバーライド）は実装しない。

## Phase 6: Lifecycle Management

### 1. 目的
- 長期運用で増加する環境定義・Dockerリソースを安全に整理し、ストレージ圧迫を防止する。
- 削除・編集操作を監査可能にし、保守性と運用品質を維持する。

### 2. 採用方針（確定）
- P6-1 削除対象の範囲: **B**
  - 定義JSON + Docker image を削除対象とする。
- P6-2 一括削除の安全レベル: **B**
  - 2段階確認（対象件数/推定解放容量の確認 + 最終確認）を必須とする。
- P6-3 未使用判定基準: **C**
  - 最終利用日時 + 利用回数 + Pin/Favorite除外で判定する。
- P6-4 Dockerクリーンアップ範囲: **B**
  - dangling + 未使用 image を対象とする（build cache は対象外）。
- P6-5 リネーム方式: **C**
  - 表示名と説明のみ編集可能、内部IDは不変とする。
- P6-6 編集可能メタデータ: **C**
  - 表示名 + 説明 + タグ/分類 + 保護フラグを編集可能とする。
- P6-7 UI構成: **B**
  - 専用 Environment Manager ダイアログを実装する。
- P6-8 監査ログ粒度: **C**
  - 成功/失敗 + 対象一覧 + 解放容量 + 実行理由を記録する。
- P6-9 失敗時ポリシー: **B**
  - 部分失敗時は継続実行し、失敗分のみ報告する。
- P6-10 強制削除権限: **B**
  - 既定で不可、明示トグル操作時のみ許可する。

### 3. 機能要件

#### R6-1 Environment Manager UI
- 専用ダイアログを提供し、環境一覧・検索/フィルタ・複数選択・削除プレビューを提供すること。
- 削除プレビューには対象件数、対象名一覧、推定解放容量を表示すること。

#### R6-2 一括削除
- 削除対象は「定義JSON + 対応Docker image」とすること。
- 2段階確認を通過しない限り削除を実行してはならない。
- 処理は対象ごとの独立実行とし、1件失敗しても残り対象は継続処理すること。

#### R6-3 未使用環境の抽出
- 未使用判定は、最終利用日時・利用回数・保護フラグ（Pin/Favorite）を入力として算出すること。
- 保護フラグ付き環境は未使用候補から除外すること。

#### R6-4 Dockerリソースクリーンアップ
- dangling image と未使用 image をクリーンアップ対象に含めること。
- build cache / volume は本フェーズの対象外とすること。

#### R6-5 リネーム・メタデータ編集
- 内部IDは変更不可とし、表示名と説明を編集可能にすること。
- 追加でタグ/分類・保護フラグを編集可能にすること。
- 編集時は入力バリデーション（空値・長さ・禁止文字等）を適用すること。

#### R6-6 監査ログ
- 削除/編集/クリーンアップ操作ごとに監査ログを生成すること。
- 最低限、操作種別、実行時刻、対象一覧、成否、解放容量、実行理由を記録すること。

### 4. UX要件
- 一括削除は常に「理解可能な影響範囲」を事前表示すること（件数・容量・対象名）。
- 部分失敗時は、成功件数・失敗件数・失敗理由を分離して提示すること。
- 強制削除は既定で無効にし、ユーザーの明示トグル操作時のみ有効化すること。

### 5. 受け入れ基準
- AC6-1: 専用 Environment Manager ダイアログから複数環境を選択して削除できる。
- AC6-2: 削除前に2段階確認が必ず表示される。
- AC6-3: 未使用候補抽出で Pin/Favorite 環境が除外される。
- AC6-4: dangling + 未使用 image のクリーンアップが実行できる。
- AC6-5: 表示名/説明/タグ/分類/保護フラグの編集が可能で、内部IDは不変。
- AC6-6: 部分失敗時に処理継続し、結果サマリ（成功/失敗）が表示される。
- AC6-7: 監査ログに必要項目（種別、時刻、対象、成否、容量、理由）が記録される。

### 6. テスト要件（必須）
- `pytest tests/` 全件 Pass を必須とする。
- 最低限、以下の自動テストを追加すること。
  - T6-1: 2段階確認ガードテスト（確認未完了で削除されない）。
  - T6-2: 未使用判定テスト（最終利用日時 + 利用回数 + 保護フラグ）。
  - T6-3: 一括削除部分失敗テスト（失敗時も残り対象を継続）。
  - T6-4: リネーム/メタデータ編集テスト（内部ID不変）。
  - T6-5: クリーンアップ範囲テスト（dangling/unused のみ対象）。
  - T6-6: 監査ログ完全性テスト（必要項目の欠落なし）。
