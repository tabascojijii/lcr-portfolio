# Core Philosophy

## 1. 最優先原則
- 本プロジェクトは **UIと疎結合な保守性最優先** を中核方針とする。
- UI（View）は入力受理と表示更新に限定し、業務ロジックは UseCase / Domain に集約する。
- 仕様変更時に UI を壊さずロジックだけ差し替えられる構造を維持する。

## 2. アーキテクチャ原則
- Humble Object を徹底し、`MainWindow` 等のUIクラスに判断・分岐・永続化ロジックを持たせない。
- 依存方向は `UI -> UseCase -> Domain -> Infrastructure` を守る。
- 境界越えは Port/Interface 経由で行い、直接依存を避ける。
- 内部IDは不変とし、表示名/説明などの可変情報はメタデータとして扱う。

## 3. 品質と安全性の原則
- 「動く」だけでなく「監査可能で再現可能」であることを品質要件とする。
- 監査不変条件:
  - 相対パス強制（絶対パスは fail-fast）
  - ハッシュ対象完全化（入力・出力・実行ログ本体・主要パラメータ）
- ガードレールを優先し、危険操作はデフォルト禁止・明示解除でのみ許可する。

## 4. UX原則
- ユーザーに「何が起きるか」を事前に明示する（件数・影響範囲・推定解放容量）。
- 破壊的操作は2段階確認を基本とし、誤操作耐性を確保する。
- 部分失敗は処理継続し、成功/失敗を分離表示して再実行可能性を高める。

## 5. ライフサイクル管理原則（Phase 6）
- 不要環境の整理は専用UI（Environment Manager）で実施し、既存画面へ責務を混在させない。
- 未使用判定は「最終利用日時 + 利用回数 + 保護フラグ」で行う。
- 削除対象は定義JSON + Docker image とし、dangling/unused image の整理を対象とする。

## 6. 開発・運用プロセス原則
- テストは機能成功だけでなく準拠性検証を含む（アーキテクチャ・監査要件）。
- `pytest tests/` 全件Passを必須ゲートとする。
- 監査でループが発生した場合は実装責任へ押し付けず、上位設計の欠陥を優先して見直す。
- 事後分析（post mortem）を次の設計へ反映し、同型障害の再発を防ぐ。

## 7. 判断基準
- 迷ったときは以下を優先順で採用する:
1. 監査可能性（証跡・再現性）
2. 保守性（疎結合・責務分離）
3. 安全性（誤操作耐性）
4. UXの明瞭性（理解しやすさ）
5. 実装速度
