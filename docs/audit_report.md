# 統合監査レポート

## 1. 対象と前提
- 対象ファイル: `docs/audit_report.md` に記録された監査指摘（Critical 2件 / Major 1件）
- 目的: 個別不具合の列挙ではなく、共通原因を特定し、是正の優先順位と実行方針を明確化する
- テスト状況: `pytest tests/` は **32 passed / 0 failed**（品質基準適合を保証する状態には未達）

## 2. 指摘事項サマリ（再整理）
1. **データ完全性違反（Critical）**
- 履歴パスに絶対パス混在を許容し、相対パス運用ルールと不整合。

2. **改ざん検知スコープ不足（Critical）**
- 監査メタデータでハッシュ対象が限定的で、入力・出力・実行ログ本体を網羅できていない。

3. **UI層の責務逸脱（Major）**
- `MainWindow` が業務判断ロジックを保持し、Humble Object原則に反する構造。

## 3. 原因分析（統合）
### 3.1 根本原因A: 「監査要件」を実装制約として固定化できていない
- 観測:
  - 相対パス義務とハッシュ網羅義務が、実装時に“必須制約”として強制されていない。
- 背景要因:
  - 監査ルールがドキュメント上の規約に留まり、コード上の不変条件（validation / fail-fast）へ落ちていない。
- 影響:
  - 実行は成功しテストも通るが、監査適合性が後工程で崩れる。

### 3.2 根本原因B: アーキテクチャ境界（UI / UseCase / Domain）の統制不足
- 観測:
  - UI層に業務分岐が残存し、責務分離が形骸化している。
- 背景要因:
  - 「どこに置くべきロジックか」の設計ガードレール不足（レビュー観点・静的チェック・実装テンプレート不在）。
- 影響:
  - 監査ロジック追加時もUI側へ拡散しやすく、変更容易性と検証容易性が同時に低下。

### 3.3 根本原因C: テスト戦略が「機能成功」に偏り、「準拠性検証」を含んでいない
- 観測:
  - Pytest全件Passでも監査基準違反が残存。
- 背景要因:
  - 監査要件（相対パス強制、ハッシュ対象網羅、層責務）に対する自動検証テストが不足。
- 影響:
  - 品質ゲートが実質的に欠落し、リグレッションを早期検出できない。

## 4. 是正方針（優先順位付き）
### P0（即時対応: リリース前必須）
1. **監査不変条件の強制**
- 履歴保存で絶対パスを禁止（または管理下相対表現へ強制変換）。
- 違反入力は fail-fast で記録し、処理継続を禁止。

2. **ハッシュ対象の完全化**
- 入力・出力・実行ログ・主要パラメータを監査対象として列挙。
- 各SHA-256と集約ハッシュを監査レコードへ保存。

### P1（短期対応: 次スプリント）
3. **UIロジックの分離**
- `MainWindow` から判定・推薦・分岐をUseCase/Domainサービスへ移管。
- UIはイベント受理と表示反映に限定。

4. **準拠性テストの追加**
- 相対パス違反検知テスト。
- 監査ハッシュ網羅性テスト。
- UI層が業務ロジックを持たないことを担保するアーキテクチャテスト。

### P2（運用定着）
5. **レビューゲート明文化**
- PRチェックリストへ「監査不変条件」「層責務」「準拠性テスト追加」を必須項目化。

## 5. 再発防止KPI
- KPI-1: 監査レコードの相対パス率 100%
- KPI-2: 監査対象ファイルのハッシュ付与率 100%
- KPI-3: UI層の業務ロジック件数 0（アーキテクチャテストで検出）
- KPI-4: 監査基準違反によるリリース差し戻し件数 0

## 6. 結論
現状の不適合は、個別実装ミスというより **監査要件の実装強制不足と層境界統制不足** に起因する構造課題である。優先度は **P0（監査不変条件とハッシュ完全化）を最優先** とし、P1で責務分離と自動検証を実装して品質ゲートを恒常化する。

- 総合判定: **REJECT_TO_IMPLEMENT**（是正実装完了まで）
