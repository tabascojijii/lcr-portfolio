# Operations Learnings (Phase 4-6.4)

## 1. フロー運用で重要だった原則
- 要件（`requirements.md`）と実行フロー（`post-commit`）の整合を最優先で確認する。
- 監査が求める成果物パスは、Implementerが書き込み可能な場所に置く（例: `artifacts/`）。
- ループ発生時は「実装不足」だけでなく「要件・計画・フックの矛盾」を疑う。

## 2. よく起きた失敗パターン
- 要件では成果物必須だが、フック側でその生成/検証条件が未定義。
- Implementerに `docs/` 変更禁止を課したまま、成果物を `docs/` に指定してしまう。
- 監査条件が抽象的で、実測手順や合格閾値が文書化されていない。
- `artifacts` の存在を前提にしているのにディレクトリ自体が未整備。

## 3. ループを止める実践手順
1. `audit_report.md` で未達要件を番号単位（例: AC6.1-5/6/7）で特定。
2. 該当成果物の不足を「手順・一覧・閾値」で埋める。
3. `post-commit` の Implementer指示と Implement監査条件を同時に修正。
4. 再監査で「文書未達」か「実装未達」かを再分類し、差し戻し先を固定。

## 4. 文書設計のコツ
- Plan/Roadmapは「対象メソッド」「移管先UseCase」「完了条件（数値）」まで固定する。
- 「主要」「必要に応じて」など曖昧語を避け、全件・必須・0件のように断定する。
- 成果物には以下を必ず含める:
  - 抽出手順（再現可能）
  - 実測一覧（証跡）
  - 数値閾値と判定

## 5. 疎結合化で効いた進め方
- 一気に全面改修せず、残件を具体メソッド単位で潰す（P0/P1/P2）。
- UI責務を「入力収集・表示更新・UseCase呼び出し」に限定する。
- Port導入はDI配線（composition）までセットで実施する。
- 監査成果物は実コード再測定で更新し、誤検知を残さない。

## 6. 型安全導入（Phase 6.2-6.4）での推奨
- Phase 6.2: Pydantic v2 を境界DTOへ段階導入（strict + fail-fast）。
- Phase 6.3: mypy中心の静的型ゲートをCI化（`Any`/`ignore`管理を含む）。
- Phase 6.4: Port契約・DTO契約・監査契約・主要導線のゴールデン回帰を固定。

## 7. 今後の運用チェックリスト
- 要件とフックの成果物パスは一致しているか。
- Implementerが成果物を出力できる指示になっているか。
- 監査条件に成果物の存在と内容基準が含まれているか。
- 合格基準は数値で固定されているか。
- `pytest tests/` だけでなく、構造・監査ゲートも通る設計か。
