# post-commit 分岐簡素化 比較メモ（承認待ち）

作成日: 2026-05-03  
対象: `.git/hooks/post-commit`

## 1. このメモの目的

分岐簡素化を導入するかどうかを判断するため、現行方式と提案方式の差分・利点・懸念を整理する。  
本メモ作成時点では、**実装は未反映**（比較のみ）。

## 2. 現行方式（分岐を明示的に分離）

現行フローは、以下を個別ブロックで保持している。

1. 生成フェーズ  
- `[USER]` -> `[ARCHITECT]`  
- `[REJECT_TO_ARCHITECT]` -> `[ARCHITECT]`  
- `[REJECT_TO_PM]` -> `[PM]`  
- `[REJECT_TO_IMPLEMENT]` -> `[IMPLEMENT]`

2. 監査フェーズ  
- `[ARCHITECT]` 監査 -> `[AUDIT_PASS_PLAN]` / `[REJECT_TO_ARCHITECT]`  
- `[PM]` 監査 -> `[AUDIT_PASS_ROADMAP]` / `[REJECT_TO_PM]`  
- `[IMPLEMENT]` 監査 -> `[AUDIT_PASS_IMPLEMENT]` / `[REJECT_TO_IMPLEMENT]`

3. 正常前進フェーズ  
- `[AUDIT_PASS_PLAN]` -> `[PM]`  
- `[AUDIT_PASS_ROADMAP]` -> `[IMPLEMENT]`  
- `[AUDIT_PASS_IMPLEMENT]` -> `[DONE]`

## 3. 提案していた簡素化（未反映）

提案内容は「次を1つの条件に寄せる」方針。

1. Architect 起動条件の統合  
- `[USER]` と `[REJECT_TO_ARCHITECT]` を同じ分岐に統合

2. PM 起動条件の統合  
- `[AUDIT_PASS_PLAN]` と `[REJECT_TO_PM]` を同じ分岐に統合

3. Implementer 起動条件の統合  
- `[AUDIT_PASS_ROADMAP]` と `[REJECT_TO_IMPLEMENT]` を同じ分岐に統合

4. 正常前進フェーズの一部を生成フェーズ統合条件へ吸収  
- 独立した「正常前進」分岐数を削減

## 4. 変えようとしていた理由

1. 重複削減  
- 同じ職能（Architect/PM/Implementer）を呼ぶ分岐の重複を減らす。

2. メンテ性向上  
- 将来プロンプト修正時に編集箇所を減らし、更新漏れを抑える。

3. 可読性向上（条件の対称性）  
- 「差し戻し」と「監査合格後の前進」で同一職能起動になる点を表現しやすい。

## 5. 想定される懸念（承認前に要判断）

1. コミット文言の粒度低下  
- `[PM] ロードマップ作成` と `[PM] ロードマップ修正` のような意味差を失う可能性。

2. 監査トレースの読解性  
- どの経路でその職能が起動したか（前進/差し戻し）がログ上で見えづらくなる可能性。

3. 意図しない巻き込み  
- 条件統合時にタグ判定の順序ミスがあると、別分岐の動作に影響するリスク。

## 6. 承認後の実装方針（予定）

1. まずは挙動同等性を保った最小統合（条件統合のみ）  
2. コミットメッセージ粒度は維持（作成/修正の文言を分ける）  
3. 変更後にテスト用空コミットでループ遷移を確認（`[USER]` 起点）
