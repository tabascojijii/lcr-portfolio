# LCR ロードマップ（PM）

## 0. 目的・適用優先順位

- `docs/plan.md` の実装計画を実行可能なマイルストーンへ分解し、監査可能な完了条件を定義する。
- 逸脱時は機能進捗よりも基準適合を優先し、基準違反状態で次フェーズへ進まない。

- 準拠性テスト（相対パス違反検知、ハッシュ網羅性、UI層の業務ロジック不在）が全件Pass。

## 2. マイルストーン

### M1: 基準適合の初期監査と不足抽出
**目的**
- 現状実装を絶対基準に照合し、違反点・未実装点を確定する。

**主要タスク**
- R1-R3 と S1-S3 のトレーサビリティ表を確定。
- EMCS観点（SRP・依存方向・複雑度・テスト網羅・監査証跡）で現状診断。
- Docker再現性要件（digest固定、EOLリポジトリ、constraints、マルチステージ）の現状判定。

**完了条件**
- 差分対象一覧（実装・テスト・運用）を確定。
- 違反条項を `reference_standards` の章番号付きで列挙。

### M2: R1 Knowledge Update 実装
**目的**
- ビルド成功時に承認済みインポート名↔パッケージ名を安全に知識DBへ反映する。

**主要タスク**
- 知識更新ユースケースをUIから分離。
- `library.json` / `user_knowledge.json` への原子的書き込み、重複排除、整合性検証。
- 失敗時ロールバックと不変性維持。

**完了条件**
- 正常系: 承認済みペアのみ追記。
- 異常系: 書き込み失敗時に既存データ不変。
- 回帰: 再実行で重複生成なし。

### M3: R2 Real-time Feedback 実装
**目的**
- Dockerビルド進捗ログをリアルタイムにGUIへ表示し、UI応答性を維持する。

**主要タスク**
- ビルド実行とログ配送の非同期ストリーム化。
- Humble Object適用により、表示整形をPresenter/ViewModel側へ分離。
- 失敗終了時の状態通知を標準化。

**完了条件**
- 長時間ビルドでもUIフリーズなし。
- 開始から終了までログ欠落なし。
- ビルド失敗時もクラッシュせず終了状態を通知。

### M4: R3 Dynamic Refresh 実装
**目的**
- 新規環境作成後の一覧更新を再起動不要で即時反映する。

**主要タスク**
- 作成完了イベント発火とデータソース再読込。
- Signal/Slot命名規則準拠（Signal: 過去分詞、Slot: 動詞）。
- 既存環境ID保持ロジックの保全。

**完了条件**
- 新規環境が即時表示。
- 直後に実行成功。
- 既存IDが `custom-env` へ化けない。

### M5: 基盤標準準拠化（Docker・データ完全性・アーキテクチャ）
**目的**
- `reference_standards` 第2-4章への適合を実装レベルで完了する。

**主要タスク**
- Dockerfileの `FROM` digest固定、EOLリポジトリ設定、`constraints.txt` 運用、マルチステージ化。
- 実行ログに image digest / git commit hash を必須記録。
- 監査レコードのハッシュ対象を「入力・出力・実行ログ本体・主要パラメータ」に完全化し、各SHA-256と集約ハッシュを保存。
- パス記録をプロジェクトルート相対へ統一し、絶対パス入力は fail-fast で拒否。
- UseCase/Entity層のQt非依存を保証し、インターフェース経由の連携を徹底。
- `MainWindow` から業務判断ロジックをUseCase/Domainへ移管（UIはイベント受理と表示反映に限定）。
- 準拠性テスト（相対パス違反検知、ハッシュ網羅性、UI層の業務ロジック不在）を追加。

**完了条件**
- 第2-4章の必須項目に未充足なし。
- 監査ログで必須証跡を確認可能。
- 絶対パス入力は fail-fast で拒否される（相対パス率100%）。
- 監査レコードに「入力・出力・実行ログ本体・主要パラメータ」の各SHA-256と集約ハッシュが保存される（ハッシュ付与率100%）。
- `MainWindow` に業務判断ロジックが残存しない（アーキテクチャテストで検出0件）。
- 準拠性テスト3点が全件Pass。

### M6: 再検証・監査ゲート
**目的**
- S1-S3 の再検証を実施し、監査判定を通過する。

**主要タスク**
- S1: 既存環境再構築でID保持・知識適用・ビルド成功を検証。
- S2: 新規作成後の即時反映と即時実行を検証。
- S3: 失敗・キャンセル時のクラッシュ耐性、停止/ロールバック、整合性維持を検証。
- `pytest tests/` 実行結果、監査証跡、要件対応表を監査提出形式で整理。

**完了条件**
- S1-S3 全件合格。
- `pytest tests/` 全件Pass。
- EMCS M1-M5 判定で全項目Pass。

## 3. 監査運用ルール（必須）
- Builder/Validator分離を維持し、Validatorは思考過程でなく提出物（Diff・対応表・ログ）のみを審査対象とする。
- REJECT時は以下を必須記載する。
  - 失敗箇所（file path / 関数・手順）
  - 違反条項（`docs/reference_standards.md` 章・条項）
  - 違反内容（事実）
  - 修正指示（手順）
  - 再提出条件（追加テスト/証跡）

## 4. リスクと先行対策
- EOL依存の取得失敗リスク: アーカイブリポジトリ切替をM5で先行実施。
- 依存解決長時間化リスク: `constraints.txt` 固定を必須化。
- UI退行リスク: R2/R3の主要フローに回帰テストを追加し、M6前に自動化。
- 監査差し戻し反復リスク: M1で違反条項を章番号付きで明示し、修正対象を先に固定。

## 5. 実行順序（クリティカルパス）
1. M1 基準適合監査
2. M2 Knowledge Update
3. M3 Real-time Feedback
4. M4 Dynamic Refresh
5. M5 基盤標準準拠化
6. M6 再検証・監査ゲート
