# LCR ロードマップ（PM）

- 作成日: 2026-05-03
- 作成者: PM
- 参照: `docs/plan.md`, `docs/reference_standards.md`
- 目的: Phase 4 再検証を最優先で完了し、規約準拠を監査可能な形で実装完了まで導く。

## 1. ロードマップ方針

1. クリティカルパスは `全テストPass回復 -> Phase 4再検証 -> 規約準拠強化 -> 最終監査` とする。  
2. 各マイルストーンは Auditor 判定をゲートにし、未合格のまま次工程へ進まない。  
3. 監査は客観メトリクス（テスト結果、依存違反件数、複雑度、証跡欠落有無）で判定する。  
4. 監査証跡は常に相対パス・ハッシュ付きで保存し、再現可能性を担保する。

## 2. マイルストーン

### M1: ベースライン評価（Week 1）

- 目的: 現状不具合と依存リスクを可視化し、修正優先度を確定する。
- 実施内容:
1. `pytest tests/` を実行し、失敗を「テスト不備 / 実装不備 / 設計不備」に分類。  
2. Phase 4 関連（Knowledge Update / Real-time Feedback / Dynamic Refresh）の実装位置と依存を棚卸し。  
3. ベースライン結果を監査証跡として保存（ログ・実行条件・ハッシュ）。
- 完了条件:
1. 失敗一覧と原因分類表が作成済み。  
2. Phase 4 の依存マップが作成済み。  
3. ベースライン証跡が相対パスで保管済み。

### M2: P0是正（Week 1-2）

- 目的: 再検証前提として `pytest tests/` 全件Passを回復する。
- 実施内容:
1. 既存失敗テストを仕様に合わせ修正。  
2. テスト不能箇所を I/F 分離・モック可能化して単体検証可能に改善。  
3. 回帰を防ぐ最小追加テストを導入。
- 完了条件:
1. `pytest tests/` が `FAILED=0 / ERROR=0`。  
2. 失敗再発を防ぐ回帰テストが追加済み。

### M3: Phase 4 再検証（Week 2）

- 目的: Phase 4 合格基準を証拠付きで満たす。
- 実施内容:
1. 遺産救済テスト: 既存環境再構築で環境ID維持を確認。  
2. 即時反映テスト: 新規環境作成後、再起動なしでUI反映・実行可能を確認。  
3. 異常系テスト: 失敗/キャンセル時にクラッシュせず停止・ロールバック動作を確認。  
4. 上記3件を `tests/` に回帰試験として実装。
- 完了条件:
1. 再検証シナリオ3件すべて合格。  
2. Knowledge Update / Real-time Feedback / Dynamic Refresh の要件がテストで担保されている。  
3. クラッシュ0件。

### M4: 規約準拠強化（Week 2-3）

- 目的: `reference_standards.md` の必須規約を実装に反映する。
- 実施内容（優先順）:
1. Docker再現性: `FROM` digest固定、EOL archive repo 強制、constraints 強制、C/C++系 multi-stage 強制。  
2. データ完全性: `input_hash`, `output_hash`, `param_hash`, `log_hash`, `image_digest`, `git_commit` を監査証跡へ必須出力。  
3. UI規律: Humble Object 徹底、Presenter/UseCase 分離、`abc.ABC`/`Protocol` 境界定義。  
4. 命名規約: signal（過去分詞）/ slot（動詞開始）を静的チェック化。
- 完了条件:
1. 規約必須項目に未実装が0件。  
2. 生成物と実装が規約チェックに合格。

### M5: 最終統合監査（Week 3）

- 目的: DoD を満たし、REJECTトリガーが0件であることを確定する。
- 実施内容:
1. 自動検証: `pytest tests/`、Phase 4 回帰、Dockerfile生成、監査証跡生成、複雑度チェック（>10 を Fail）。  
2. 静的検証: レイヤ依存（`UI -> Domain` 逆流）、UI層業務ロジック混入、命名規約。  
3. 手動検証: GUIリアルタイムログ、即時反映、キャンセル時安定性。  
4. Validator入力を `requirement + diff + test evidence` に限定し監査判定する（3点のいずれか欠落時は即時REJECT）。
- 完了条件:
1. `pytest tests/` 全件Pass。  
2. 再検証シナリオ3件合格。  
3. 監査証跡必須6項目の欠落0件。  
4. 依存違反0件、UIロジック違反0件、複雑度違反0件。  
5. 1クラス1責務逸脱0件。  
6. REJECTトリガー該当0件。  
7. 監査入力が `requirement + diff + test evidence` に限定され、基準文書と整合している。  
8. `test evidence` 欠落時は未完了（REJECT）として扱われることが判定記録で確認できる。

## 3. 依存関係とゲート

1. M2 は M1 完了後に開始。  
2. M3 は M2（全テストPass）をゲートとして開始。  
3. M4 は M3（Phase 4 合格）をゲートとして開始。  
4. M5 は M4（規約準拠完了）をゲートとして開始。  
5. いずれかのゲートで不合格の場合は直前マイルストーンへ差し戻し。

## 4. 監査判定基準（REJECT条件）

1. `pytest tests/` に 1件でも失敗/エラーがある。  
2. 再検証シナリオ3件のうち1件でも未合格。  
3. 監査証跡6項目のいずれか欠落、またはハッシュ不整合。  
4. `UI -> Domain` 逆流が1件でも存在。  
5. UI層で Presenter/UseCase を介さない業務処理が1件でも存在。  
6. 関数循環的複雑度 > 10 が1件でも存在。  
7. 1クラス1責務逸脱が1件でも存在。  
8. 監査入力3点セット（`requirement + diff + test evidence`）のいずれかが欠落している。  

## 4.1 正本優先順位（解釈ルール）

1. 仕様解釈の正本優先順位は `docs/plan.md` > `docs/roadmap.md` > `docs/reference_standards.md` とする。  
2. 下位文書が上位文書と不一致の場合、上位文書を正として是正し、監査時は不一致自体を指摘対象に含める。

## 5. 成果物

1. `docs/roadmap.md`（本書）  
2. `src/` 実装差分（Phase 4 + 規約準拠）  
3. `tests/` 追加・修正（再検証シナリオ含む）  
4. 監査エビデンス一式（テスト結果・実行ログ・各種ハッシュ・検証記録）

## 6. リスク管理

1. 旧環境データ差異でID保持が崩れる。  
対応: 互換レイヤと回帰テストを先行実装。  
2. GUIテストの実行環境依存が強い。  
対応: Presenter中心の単体試験を主軸にし、GUI統合試験を最小化。  
3. EOL依存取得が不安定。  
対応: archive repo + constraints をテンプレートで必須化し、未設定は即時エラー。
