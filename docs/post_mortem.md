# 事後分析レポート（Post Mortem）

## 1. 事象
- 2026-05-04時点の監査結果は `docs/audit_report.md` にて **REJECT_TO_ARCHITECT**。
- 差し戻し理由は実装バグではなく、`docs/plan.md` 上の設計定義不足（High 2件、Medium 1件）。
  1. Data Integrity のハッシュ対象が全件必須として確定されていない（「主要パラメータ」という限定語）。
  2. Clean Architecture 制約で `UseCase -> Qt` 禁止が明文化されていない。
  3. Humble Object 制約で「UIの複雑計算/フォーマット処理禁止」が明文化されていない。

## 2. 無限ループの構造
- 発生ループ: `設計定義不足のまま実装依頼 -> 監査で設計不足を検出 -> 実装に再指示 -> 設計不足が残存 -> 再度REJECT`。
- 本質は「実装品質」ではなく「設計仕様の可監査性不足」。実装側の努力では閉じないループである。

## 3. 根本原因（Root Cause）

### RC-1: 要件の完全性を担保する設計文法が未整備
- `reference_standards.md` は「すべての入出力・パラメータ・実行ログ」のハッシュを要求。
- `plan.md` は「主要パラメータ」と記載し、監査可能な全件定義に落ちていない。
- 結果として、実装時に対象範囲の解釈が揺れ、監査で確実に差し戻される。

### RC-2: アーキテクチャ境界の禁止依存が不完全
- `UseCase -> Qt` 禁止が非許可依存に明記されておらず、設計時点で逸脱余地を残した。
- 依存方向ルールが一部欠落した状態では、実装レビューと静的検査の双方で判定基準が不安定になる。

### RC-3: UI責務制約が「行為禁止」まで具体化されていない
- Humble Object の要求（UIから計算/整形を排除）が仕様化されていない。
- 「判断・分岐・I/O禁止」だけでは不十分で、UIにロジックが再流入する構造を止められない。

## 4. 是正方針
- 本件は **Implementerへの追加実装指示では解決不可**。
- **Architect が上位設計を再定義し、監査基準を満たす文書へ改訂後に実装再開**とする。
- 必須改訂項目:
  1. ハッシュ対象を `all_input_files / all_output_files / all_parameter_files / audit_log_record` として全件必須明記。
  2. 非許可依存に `UseCase -> Qt` を追加し、CIに検出ルールを追加。
  3. UI責務制約に「複雑計算・フォーマット処理禁止」を明記し、検査ゲート化。

## 5. 再発防止（運用）
- REJECTルーティングを厳格適用する。
  - 設計不備: `REJECT_TO_ARCHITECT`
  - 実装不備: `REJECT_TO_IMPLEMENT`
- 監査報告の必須項目（失敗箇所、違反制約、観測証拠、修正ヒント、再検証条件、ルーティング先）欠落時は監査失敗とする。
- `pytest` pass とは独立に、設計適合ゲート（依存方向、UI責務、監査スキーマ全件性）をリリース前提条件化する。

## 6. 結論
- 無限ループの根本原因は、`docs/plan.md` の上位設計が絶対基準を満たす粒度まで固定されていなかったことにある。
- 従って、対処の主語は Implementer ではなく Architect であり、抜本的な再設計を起点に是正する。
