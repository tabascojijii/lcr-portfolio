# 事後分析レポート（Post Mortem）

## 1. 事象
- 監査結果は `pytest` Pass（34件）にもかかわらず、規約準拠で **REJECT_TO_IMPLEMENT** となった。
- 差し戻し理由は、単純な実装修正ではなく、以下の上位設計不備を含んでいた。
  - Data Integrity（監査証跡スキーマの不足）
  - UIアーキテクチャ境界（Humble Object / Clean Architecture の未充足）

## 2. 影響
- Implementer に差し戻しても、修正対象が「関数追加」ではなく「責務境界の再定義」を要するため、局所パッチが増え、再監査で同系統の指摘が再発する。
- その結果、`REJECT_TO_IMPLEMENT -> 実装修正 -> 再監査 -> REJECT_TO_IMPLEMENT` の循環に入りやすい。

## 3. 根本原因（Root Cause）

### RC-1: 要件を満たす「監査ログ最小スキーマ」が設計段階で確定していなかった
- 監査基準は「入出力・パラメータ・実行ログ自体のハッシュ」を必須としている。
- しかし実装は `script_sha256` 中心で、証跡対象の定義（何を、いつ、どの単位でハッシュ化するか）がアーキテクチャ成果物として固定されていなかった。
- 結果として、実装者は局所的な追加対応になり、監査観点の網羅性を担保できなかった。

### RC-2: UI層とUseCase層の境界定義が不十分なまま実装が進んだ
- `MainWindow` が分析実行、定義生成、保存、ビルド起動、履歴更新、監査追記まで抱え、責務が集中。
- これは実装品質の問題というより、先に「どこまでをUI責務とし、どこからをUseCase/Portに置くか」を固定しなかった設計プロセス上の問題。
- そのため Implementer が修正しても、同じクラスに処理が再流入しやすく、再発防止が効かない。

### RC-3: 差し戻し先のルーティングが違反の性質と不整合
- 今回の違反は「実装バグ」ではなく「設計境界・要件分解の不足」が主因。
- にもかかわらず最終判定が `REJECT_TO_IMPLEMENT` のみだと、構造的課題が実装レイヤーに押し込まれ、是正責任と権限が一致しない。
- これが無限ループの直接トリガーになった。

## 4. なぜ検知・収束できなかったか
- `pytest` Pass が品質ゲートとして強く見え、アーキテクチャ適合性ゲート（責務境界、監査スキーマ完全性）が相対的に後追い化した。
- 監査で設計違反は検知できたが、エスカレーション先が実装レイヤー固定になり、是正経路が閉じた。

## 5. 再発防止策

### 5.1 即時是正（今回案件）
- 本件は **Implementer への追加実装指示で解決しない**。
- **Architect へ差し戻し、上位設計からやり直す**。
- 最低限、以下を設計成果物として確定後に実装再開する。
  1. 監査ログ必須スキーマ（対象ファイル群、採取タイミング、保存形式、検証方法）
  2. UI / UseCase / Infra の責務境界図とPort定義
  3. 「UIから直接呼んでよい操作」の許可リスト（禁止API含む）

### 5.2 プロセス是正（恒久対応）
- REJECT分類を2系統化する。
  - 実装不備: `REJECT_TO_IMPLEMENT`
  - 設計不備: `REJECT_TO_ARCHITECT`
- 監査票に「違反原因レイヤー（Requirement / Architecture / Implementation）」を必須項目として追加する。
- `pytest` とは別に、アーキテクチャゲート（依存方向、責務過密、必須監査項目充足）を通過条件化する。

## 6. 結論
- 無限ループの根本原因は、個別実装の巧拙ではなく、**監査要件とアーキテクチャ境界を先に固定しないまま実装フェーズへ進んだ上位設計不備**である。
- よって本件の正しい是正は、Implementer への再指示ではなく、**Architect 主導の抜本再設計**を起点に進めることである。
